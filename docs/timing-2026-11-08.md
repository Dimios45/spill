# Repeated local timing failures — 2026-11-08

## Evidence

Hardware runs repeatedly paired an execution deadline miss (~130–141 ms late)
with mixed-age camera/state snapshots (~150–178 ms spread). Different cameras
and arms were old on different runs. Dream requests immediately before these
failures generally succeeded in ~0.7–0.9 seconds. The failure is raised by local
execution/observation checks, not a Dream API error. This does not exclude other
sources of host load or capture delays.

The recording preflight imported `lerobot.datasets.lerobot_dataset`, bringing
PyTorch/datasets and their large object graph into the controller process before
motion. In a separate offline measurement, tracked objects grew from ~5,400 to
~371,000; three full generation-2 garbage collections took 112.8, 113.2 and
115.6 ms, versus 0.2 ms before the imports. An instrumented mock process with the
imports observed a 117.9 ms heartbeat gap coincident with 116.3 ms full GC during
setup (before its manifest). That is a reproduced source of long local stalls,
not proof that all earlier hardware faults were GC. Those episodes lacked GC
telemetry.

A 70-second offline control probe without those export imports completed without
heartbeat gaps above 50 ms; its measured full collections were 27–32 ms. Mock
arms and no API calls were used. Hardware camera/native receive work is absent,
so this test cannot establish hard real-time guarantees for the physical rig.

## Changes

- Export dependency preflight runs in a bounded child process before hardware
  startup. Import success and the LeRobot v3 version are still checked. Export
  itself remains after shutdown. Raw observation and command recording continue.
- Long Python garbage collections (>=20 ms) are now recorded as `python_gc_pause`
  with start/end time and generation, allowing correlation on the next trial.
  GC is not disabled and timestamps/guard thresholds are unchanged.
- Dream-only checkpoints preserve the ongoing model session. Previously, every
  20-second checkpoint called `reset_episode`, clearing model history and chunk
  blending. Explicit replans/resumes still reset as before. The checkpoint still
  finishes the chunk and performs the existing guarded hold; this change is not
  asynchronous streaming or a removal of safety checks.

## Dream documentation

The installed official SDK is `dreamlabs-client` 1.0.14. Its `reset_episode`
docstring says to call it between episodes: it ends the session, clears model
memory and resets chunk blending. See the installed `dream/client.py` and the official [changelog](https://github.com/dreamlabs-co/dreamlabs/blob/main/dream_library/dream_client/CHANGELOG.md).
The public [Dream-1 research page](https://dreamlabs.ai/research/dream-1/) describes
chunked action generation but does not prescribe relaxing local freshness checks.
The platform landing page was inaccessible through the documentation browser;
local installed SDK source was used to verify reset semantics.

## Post-fix offline validation

Instrumented mock run `20261108T121458-75d68c5b` used Viser, recording and the
isolated export preflight for 70 seconds. It completed with zero interventions,
three same-session reporting checkpoints, no measured heartbeat gaps above
50 ms during control, and no GC collections above 20 ms during control. All
1,400 dataset frames exported after shutdown. Longer pauses reappeared during
post-shutdown export, outside the control interval. This validates separation of
the export workload, not physical camera/USB/native-feedback performance.
